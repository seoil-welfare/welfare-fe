## 1. 미수정 기능 → 수정 완료

### 1-1. 보고서 오류와 출력 기능

**보고서에 기록하지 않은 지원 결과가 만들어지는 문제**

수정되지 않음 → **수정 완료**

- 수정 전: 반응이나 행동 선택만 보고 ‘지원 후 안정·재참여’ 같은 결과 문장을 자동으로 만들었다.
- 수정 후: 기록에 없는 결과를 만들어 넣는 처리를 없앴다. 저장된 활동·지원·반응·특이사항을 사용한다.

**일별·월별 보고서에 제공한 새 양식 연결**

추가 요청 미반영 → **구현 완료**

- 수정 전: 추가로 제공한 일별·월별 양식이 그대로 연결된 상태가 아니었다.
- 수정 후: 일별 버튼은 일별 양식, 월별 버튼은 월별 양식으로 내려받는다. 이용자·기간에 맞는 작성 완료 일지를 사용한다.

**보고서에 앱에서 입력할 수 없는 항목이 있는 문제**

양식 정리 필요 → **정리 완료**

- 수정 전: 제공한 양식에는 주요 목표·지원 결과·선행사건·인수인계·월간 평가 등이 있었지만 앱에는 따로 입력할 칸이 없었다.
- 수정 후: 사용자 결정에 따라 해당 칸을 양식에서 뺐다. 빈칸을 임의의 문장으로 채우지 않는다.

**행동 선택 건수를 실제 발생 횟수처럼 표시하는 문제 — PPT 09-01**

수정되지 않음 → **수정 완료**

- 수정 전: 행동 항목을 선택한 수를 ‘몇 회’로 표시했다.
- 수정 후: ‘몇 건’으로 표시한다. 실제로 몇 번 발생했는지와 구분한다.

**보고서의 행동 이름만으로 종류를 구분하기 어려운 문제 — PPT 09-02**

수정되지 않음 → **수정 완료**

- 수정 전: 행동 이름에 자해·타해 등의 구분이 항상 붙지 않았다.
- 수정 후: 행동 이름에 구분을 붙였다. 같은 이름의 행동도 종류를 구분할 수 있다.

**출력 기간에 미래 날짜를 선택할 수 있는 문제 — PPT 09-03**

수정되지 않음 → **수정 완료**

- 수정 전: 오늘 이후 날짜를 출력 종료일로 지정할 수 있었다.
- 수정 후: 미래 날짜·잘못된 날짜·시작과 끝이 뒤집힌 기간·92일 초과를 막는다.

**보고서와 통계의 행동 수 계산 방식이 달라질 수 있는 문제 — PPT 12-05**

일부 보완 필요 → **수정 완료**

- 수정 전: 보고서와 통계가 행동을 세는 방식이 따로 있어, 중복 선택이나 비어 있는 ‘기타’를 다르게 처리할 여지가 있었다.
- 수정 후: 같은 기준으로 세도록 맞췄다. 중복 항목과 내용 없는 ‘기타’도 검사했다.

**긴 표가 다음 페이지로 넘어가면 열 제목이 사라지는 문제**

수정되지 않음 → **수정 완료**

- 수정 전: 다음 장에서 시간·활동 내용·지원 등의 열 제목을 다시 볼 수 없었다.
- 수정 후: 표가 이어지는 장에도 열 제목이 반복되도록 바꿨다.

### 1-2. 로그인·홈 화면

**완료 일지를 수정하다 나갈 때 일부 활동 입력을 놓칠 수 있는 문제 — PPT 04-01**

일부 수정 → **수정 완료**

- 수정 후: 활동 편집 중인 내용도 나가기 전 경고에 포함했다.

**긴 활동 내용·특이사항이 읽기 어렵게 줄바꿈되는 문제 — PPT 04-02**

수정되지 않음 → **수정 완료**

- 수정 후: 한국어 단어와 긴 문자열이 화면 너비에 맞게 줄바꿈되도록 보완했다.

## 2. 코드와 처리 방식에서 아직 부족한 점

아래 내용은 현재 코드를 추가로 읽고 정리한 것이다. **코드에서 구조를 확인한 사항과 실제 발생을 재현한 오류는 다르다.** 다음 항목을 모두 새 오류로 재현했다는 뜻은 아니다. 이번 요청에서는 문서로 정리했으며, 아래 개선을 추가 구현한 것은 아니다.

### 2-1. 저장 관련 처리가 한 파일에 많이 모여 있음

**현재 상태: 구조 개선 여지 있음**

- 부족한 점: 작성 중 내용, 자동 저장, 저장 충돌, 화면 나가기 경고, 복원, 활동 이름 변경 처리를 `DraftContext.tsx` 한 파일에서 함께 관리한다.
- 왜 아쉬운가: 저장 방식 하나를 고쳐도 나가기 경고나 복원에 영향을 줄 수 있어 수정할 때 확인할 범위가 넓다.
- 개선 방향: ‘입력 보관’, ‘서버에 저장’, ‘나가기 보호’, ‘다른 사람 수정 알림’을 나누고 연결 지점을 명확히 한다.
- 확인한 코드: `welfare-fe/src/app/DraftContext.tsx`.

### 2-2. 바뀐 내용을 확인할 때 일지 전체를 글자로 바꿔 비교함

**현재 상태: 구조 개선 여지 있음**

- 부족한 점: 일지 전체를 하나의 긴 문자열로 만들어 이전 내용과 비교한다.
- 왜 아쉬운가: 활동과 글이 많아지면 입력할 때 비교하는 자료도 커진다. 어떤 항목이 바뀌었는지도 직접 알기 어렵다.
- 개선 방향: 실제 성능을 측정한 뒤, 바뀐 부분을 따로 표시하거나 비교 전용 함수를 둔다.
- 확인한 코드: `DraftContext.tsx`의 `contentKey`.
- 구분: 현재 앱이 느리다는 것을 측정한 결과는 아니다.

### 2-3. 화면과 서버에 같은 업무 규칙이 각각 들어 있음

**현재 상태: 기준을 계속 맞춰야 함**

- 부족한 점: 시간·반응·비밀번호·통계 기간 규칙을 화면 코드와 서버 코드에서 각각 처리한다.
- 왜 아쉬운가: 한쪽만 고치면 화면에서 허용한 입력을 서버가 거절하거나, 서로 다른 기간을 계산할 수 있다.
- 개선 방향: 화면의 빠른 안내와 서버의 최종 검사는 모두 유지하면서, 같은 예시로 양쪽을 비교하는 검사를 관리한다.
- 확인한 코드: FE `activityTime.ts`, `accountValidation.ts`, `statsService.ts`와 BE `ActivityTime.java`, `PasswordPolicy.java`, `StatsPeriod.java`.
- 구분: 이번에 바꾼 규칙은 맞추고 검사했다. ‘검사가 두 군데 있으니 한쪽을 없애자’는 의미는 아니다.

### 2-4. 화면의 활동 선택값에 이름이 들어가 이름 변경 처리가 복잡함

**현재 상태: 같은 화면 안은 보완 완료 / 여러 화면 동기화는 추가 확인 필요**

- 부족한 점: 서버는 활동의 고유 번호를 저장하지만 화면의 작성 중 자료는 이름을 사용한다.
- 왜 아쉬운가: 이름을 바꿀 때 작성 중인 내용까지 찾아 바꿔야 한다. 현재 즉시 알림은 같은 앱 실행 안의 구독자에게 전달한다.
- 개선 방향: 화면도 고유 번호와 표시 이름을 함께 다루는 방식, 다른 탭·다른 직원 화면의 갱신 기준을 검토한다.
- 확인한 코드: `participationChanges.ts`, `DraftContext.tsx`, BE `Catalog.java`.
- 구분: 다른 계정에서 이름을 바꾸는 상황의 즉시 반영은 이번에 별도 재현한 결과가 아니다.

### 2-5. 서버가 잘못된 형식의 답을 보내면 오류를 명확히 알려주지 않음

**현재 상태: 아직 보완할 부분 있음**

- 부족한 점: 서버 응답을 읽다가 형식이 잘못되면 `null`로 바꾸고, 성공 응답이라면 기대한 자료인 것처럼 돌려줄 수 있다.
- 왜 아쉬운가: 사용자에게 ‘자료가 잘못 도착했다’고 알려주기보다 빈 화면이나 다른 문제로 보일 수 있다.
- 개선 방향: 정상 자료가 필요한 요청은 형식까지 검사하고, 잘못된 응답은 분명한 오류로 처리한다.
- 확인한 코드: `welfare-fe/src/api/http/client.ts`의 `readJson`, `request`.
- 구분: 잘못된 성공 응답을 보내는 운영 장애를 실제로 재현한 것은 아니다. 코드의 예외 처리 빈틈을 확인한 것이다.

### 2-6. 서버 응답을 너무 오래 기다릴 때 끊는 공통 기준이 없음

**현재 상태: 아직 보완할 부분 있음**

- 부족한 점: 요청을 취소하는 값을 받을 수는 있지만, 공통으로 정한 ‘일정 시간 뒤 중단’ 처리는 없다.
- 왜 아쉬운가: 연결이 늦거나 멈춘 상황에서 사용자가 기다리는 시간이 길어질 수 있다.
- 개선 방향: 오래 걸린 요청의 중단·재시도 기준을 정하고, 화면을 나갔을 때 필요 없는 조회도 취소하도록 연결한다.
- 확인한 코드: `welfare-fe/src/api/http/client.ts`, `src/api/queries.ts`.
- 구분: 모든 요청이 멈춘다는 뜻은 아니다.

### 2-7. 앱을 닫는 순간의 저장은 성공 답을 확인할 수 없음

**현재 상태: 처리 한계가 남아 있음**

- 부족한 점: 탭이 닫힐 때도 저장 요청을 보내지만, 닫히는 중에는 성공 답을 끝까지 기다릴 수 없다.
- 왜 아쉬운가: 연결이 끊기거나 모바일에서 앱이 강제 종료되면 마지막 입력이 저장됐는지 보장하기 어렵다.
- 개선 방향: 저장 실패·미확인 상태를 다시 접속했을 때 확인하는 방법과 실제 기기 검사를 보강한다. 기기에 기록을 남기지 않는 기존 원칙도 함께 검토해야 한다.
- 확인한 코드: `DraftContext.tsx`, `src/api/http/httpApi.ts`의 `saveDiaryBeforeUnload`.

### 2-8. 일지 수정 시 활동을 전부 지우고 다시 넣음

**현재 상태: 정상 동작하지만 구조 개선 여지 있음**

- 부족한 점: 일지 일부만 고쳐도 그 일지의 활동 자료를 모두 교체한다. 변경이 실제 반영되는 경우 활동의 번호도 새로 발급된다.
- 왜 아쉬운가: 활동이 많으면 저장 작업이 늘고, 같은 활동의 변경 과정을 계속 추적하기 어렵다.
- 개선 방향: 바뀐 활동만 고치는 방식과 활동 번호를 유지할 필요가 있는지 검토한다.
- 확인한 코드: BE `DiaryService.java`의 `update`, `DiaryRepository.java`의 `deleteRecords`, `insertRecord`.
- 구분: 저장은 한 묶음으로 처리되어 중간 실패 시 되돌리는 장치가 있다. 현재 자료가 유실된다는 뜻은 아니다.

### 2-9. 일지 목록을 한 번에 많이 가져올 수 있음

**현재 상태: 많은 자료에 대한 개선 여지 있음**

- 부족한 점: 서버 일지 목록 조회는 조건에 맞는 자료를 한 번에 가져오며, 몇 개씩 나눠 받는 장치가 없다.
- 왜 아쉬운가: 이용자와 기록이 많아지면 한 번의 조회·전송에 필요한 양이 커질 수 있다.
- 개선 방향: 화면 용도별 조회 범위를 정하고, 목록은 나눠 가져오거나 꼭 필요한 정보만 받도록 검토한다.
- 확인한 코드: BE `DiaryRepository.java`의 `findLogs`.
- 구분: 보고서 화면에는 기간 제한이 있다. 이 항목은 서버의 공통 목록 조회 구조에 대한 내용이며, 대용량 지연을 측정한 결과는 아니다.

### 2-10. 통계 화면과 보고서가 서로 다른 곳에서 자료를 계산함

**현재 상태: 현재 기준은 검사했지만 장기 관리 필요**

- 부족한 점: 통계 화면의 자료는 주로 서버가 계산하고, 보고서는 브라우저가 일지를 읽어 계산한다.
- 왜 아쉬운가: 계산 규칙을 바꿀 때 두 경로를 함께 고쳐야 한다.
- 개선 방향: 동일한 입력에 대해 서버 통계와 보고서 숫자가 같은지 비교하는 검사를 계속 유지한다.
- 확인한 코드: BE `StatsService.java`, `StatsRepository.java`, FE `monthlyRecordService.ts`, `statsService.ts`.

### 2-11. 보고서 만들기를 사용자의 기기에서 처리함

**현재 상태: 많은 자료를 출력할 때 개선 여지 있음**

- 부족한 점: 일지를 받아 표·그림·문서 파일을 모두 브라우저에서 만든다.
- 왜 아쉬운가: 많은 사람이나 긴 기간을 출력하면 휴대폰의 속도와 메모리 영향을 받을 수 있다.
- 개선 방향: 실제 출력량을 측정하고, 필요하면 서버에서 파일을 만들거나 작업을 나누는 방법을 검토한다.
- 확인한 코드: `src/lib/export/downloadDailyRecord.ts`, `downloadMonthlyRecord.ts`.
- 구분: 현재 검사 범위의 파일 생성·다운로드는 성공했다. 실제 기기의 대량 출력 성능은 별도 확인이다.

### 2-12. 여러 명의 월별 보고서를 순서대로 만들고 중간 취소가 없음

**현재 상태: 아직 보완할 부분 있음**

- 부족한 점: 이용자를 한 명씩 처리하고 파일마다 다운로드한다. 실행 중 멈추는 전용 기능은 없다.
- 왜 아쉬운가: 대상이 많으면 기다리는 시간이 늘고, 파일도 여러 개로 나뉜다.
- 개선 방향: 진행 상황 표시, 중간 취소, 실패한 대상만 다시 만들기, 파일 묶음 다운로드를 검토한다.
- 확인한 코드: `MonthlyRecordForm.tsx`의 `run`.

### 2-13. 보고서 실패 이유를 자세히 구분하지 않음

**현재 상태: 아직 보완할 부분 있음**

- 부족한 점: 월별 출력에서 실패한 이용자 이름은 보여주지만, 조회 실패인지 양식 문제인지 등을 구분해 보여주지는 않는다.
- 왜 아쉬운가: 사용자가 다시 시도해야 하는지, 관리자에게 알려야 하는지 판단하기 어렵다.
- 개선 방향: 실패 이유를 나누고 재시도 가능한 경우를 안내한다.
- 확인한 코드: `MonthlyRecordForm.tsx`의 `catch`, `MonthlyResultAlert`.

### 2-14. 월별 요약의 활동·지원·반응이 같은 활동에서 나온 값이라고 오해할 수 있음

**현재 상태: 요약 방법의 한계가 있음**

- 부족한 점: 하루 동안 가장 많이 고른 활동, 가장 많이 고른 지원, 가장 많이 고른 반응을 각각 뽑아 한 줄로 놓는다.
- 왜 아쉬운가: 세 값이 반드시 같은 활동에서 나온 조합은 아니다.
- 개선 방향: ‘하루의 대표 선택값’이라는 설명을 유지하고, 특정 활동과 반응의 관계를 보여줄 때는 실제 같은 활동끼리 묶는다.
- 확인한 코드: `monthlyRecordService.ts`의 `topLabel`, `dayRow`.
- 구분: 현재 표도 대표 항목 요약으로 만든 것이다. 지원 효과를 증명하는 자료로 해석해서는 안 된다.

### 2-15. 보고서 양식을 바꾸려면 코드의 칸 설정도 고쳐야 함

**현재 상태: 유지보수 개선 여지 있음**

- 부족한 점: 양식 생성 코드가 표 두 개와 정해진 열 위치를 기준으로 동작한다.
- 왜 아쉬운가: 원본 양식에 열을 추가하거나 순서를 바꾸면 코드도 함께 확인해야 한다.
- 개선 방향: 칸과 데이터의 연결을 한곳에 정리하고, 양식이 바뀌면 바로 오류를 알려주는 검사를 유지한다.
- 확인한 코드: `scripts/build-report-templates.cjs`.

### 2-16. 작성자 이름을 찾지 못하면 보고서에 빈칸으로 남음

**현재 상태: 사용자 안내 보완 여지 있음**

- 부족한 점: 저장된 작성자 번호에 맞는 직원 정보를 찾지 못하면 이름을 비운다.
- 왜 아쉬운가: 사용자가 미입력인지 자료 누락인지 알기 어렵다.
- 개선 방향: ‘작성자 정보 확인 필요’처럼 상황을 알려주거나, 기록 당시 작성자 이름을 보존할 필요가 있는지 검토한다.
- 확인한 코드: `dailyRecordService.ts`, `monthlyRecordService.ts`.
- 구분: 임의의 이름을 넣지 않는 현재 처리는 맞다. 누락을 알려주는 방식에 대한 개선 의견이다.

### 2-17. 새 보고서에서 쓰지 않는 예전 출력용 값이 일부 남아 있음

**현재 상태: 정리 여지 있음**

- 부족한 점: 일별 출력 자료에 생년월일 6자리와 예전 행동 체크칸 값 등이 남아 있다. 현재 출력 양식에서는 사용하지 않는다.
- 왜 아쉬운가: 어떤 값이 실제 보고서에 필요한지 파악하기 어렵다.
- 개선 방향: 사용하는 검사·호출부까지 확인한 뒤 필요 없는 값과 주석을 함께 정리한다.
- 확인한 코드: `dailyRecordService.ts`의 `birth6`, `noneMark`, `someMark`와 현재 DOCX 양식.
- 구분: 파일 출력 오류는 아니다. 일부 기존 검사에서 사용하므로 무조건 지우면 안 된다.

## 3. 기능 자체에서 아직 남아 있는 점

### 종결 이용자의 일괄 보고서 출력

**아직 남아 있음**

- 현재: 종결 이용자의 통계는 볼 수 있지만 일별·월별 출력 메뉴에서는 이용 중인 사람만 고를 수 있다.
- 필요한 개선: 출력 대상에도 ‘종결 이용자 포함’ 선택을 추가하는 방안.
- 코드: `ExportPage.tsx`의 `activeServiceUsers`.

### 오래된 월별 기록 출력

**아직 남아 있음**

- 현재: 월별 출력의 연도 선택지는 최근 5개 연도다.
- 필요한 개선: 더 오래된 기록이 필요한 경우 연도 선택 범위를 넓히거나 직접 연도를 입력하는 방안.
- 코드: `MonthlyRecordForm.tsx`의 `MONTHLY_YEAR_COUNT`.

### 실제 행동 발생 횟수·지속 시간 기록

- 필요한 개선: 추후 평가 보고서가 필요할 때 입력 기능부터 추가해야 한다.
- 구분: 지금 다시 채워 넣어야 하는 미수정 오류로 분류하지 않는다.

### 서버를 재시작한 뒤 로그인 유지

## 4. 아직 실제 환경에서 확인하지 않은 부분

- 운영 계정으로 실제 화면 → 실제 서버 → 운영 DB → 통계 → 보고서까지 연결한 전체 과정.
- 실제 휴대폰에서 앱 강제 종료·통신 끊김·재접속 후 마지막 입력 복구.
- Safari와 실제 기기 키보드·주소창 환경.
- Microsoft Word 자체에서 연 배치와 종이 인쇄. 지금까지의 인쇄 배치 확인은 LibreOffice에서 만든 PDF 기준이다.
- 많은 이용자·오래 쌓인 기록을 실제 기기에서 조회하고 한꺼번에 출력하는 속도.

이 항목들은 **추가 확인 필요**이며, 이미 발생한 오류라고 단정하지 않는다.
